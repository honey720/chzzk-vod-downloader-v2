# 릴리즈 규칙 — 버전 · rc · 정식

릴리즈 절차(Version Bump 실행, `dev-*` → `main` PR과 머지)는 **소유자가 한다.** 에이전트는 요청받은 확인만 한다.

## 버전

- **유저가 체감하는 변경은 마이너, 내부 재설계·버그 수정은 패치.** 타임라인·재생기 보완은 패치로 낸다.
- 버전은 역행하지 않는다.
- ⚠️ 버전 문자열에 `-`를 넣으면 Auto Tag가 rc로 판정해 태그와 빌드를 만든다. **rc가 아닌 목적으로 `-`가 든 버전을 쓰지 않는다.**

## rc

rc는 `dev-*`의 한 시점을 태그로 고정해 **릴리즈 워크플로우로 실제 빌드한 것**이다. `dev-*`의 CI는 테스트만 돌리고 실행 파일을 만들지 않는다 — 실행 파일에서만 드러나는 문제는 rc에서 확인한다.

- **마이너 릴리즈는 rc를 찍는다.**
- **패치는 실행 파일 위험 표면을 건드릴 때 찍는다** — 의존성 · 리소스·파일 경로 · 런타임 조회 · 빌드 설정 · 동봉물. 변경 크기로 위험을 판단하지 않는다.
- rc 태그는 `dev-*` 커밋에 붙는다. rc는 `dev-*` 안에서 반복하고, 찍을 때마다 그 시점이 새 기준이 된다.
- ⚠️ **정식 = 마지막 rc + 버전 파일 bump.** 마지막 rc 뒤에 다른 커밋이 들어가면 rc를 다시 찍는다.

## 절차

1. Version Bump를 **`dev-*`에서** 실행한다. rc·정식 모두 `dev-*`로 PR이 간다
2. rc bump 머지 → `dev-*` 커밋에 rc 태그 → 프리릴리즈 빌드
3. 정식 bump를 `dev-*`에 머지한다. `dev-*`에서는 정식 태그가 생기지 않는다
4. **`dev-*` → `main` 머지.** 그 머지 커밋에 정식 태그가 붙고, 정식 빌드와 rc 태그·릴리즈 정리가 따라온다. `main`이 바뀌는 것은 릴리즈당 이 한 번이다
5. `dev-*`는 머지와 함께 지워진다

- ⚠️ **4의 PR은 merge commit으로 머지한다. squash를 쓰지 않는다.** squash는 커밋을 새로 만들어 rc 태그가 가리키는 커밋이 `main` 이력에서 끊긴다 — 정식이 rc와 같은 것인지 git으로 확인할 수 없게 된다.

## 확인

| 언제 | 무엇 | 통과 조건 |
|---|---|---|
| 4 전 | `git merge-base --is-ancestor origin/main dev-<버전>` | 참. 거짓이면 동기화(`branch.md`)부터 |
| 4 뒤 | `git diff v<버전>-rc<N> v<버전>` | 버전 파일 셋(`pyproject.toml` · `uv.lock` · `APP_VERSION`)만 바뀜 |

## 릴리즈 노트

- 출시되지 않은 코드의 버그 수정은 넣지 않는다. 검증되지 않은 항목은 넣지 않는다.
- 분류는 **PR 라벨** 기준이다. `dev-*` → `main` PR에는 `chore` 라벨을 달아 노트에서 뺀다.
