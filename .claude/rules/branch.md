# 브랜치 규칙

```
main                              배포된 것만 들어온다
 └ dev-<버전>                      그 버전 개발이 모이는 곳. 예: dev-2.11.0 · dev-2.10.2
    └ <타입>/<이슈번호>-<짧은-설명>  작업 하나. 예: feat/12-url-drag-drop
```

| | 마이너 dev | 패치 dev |
|---|---|---|
| 이름 | `dev-X.Y.0` | `dev-X.Y.Z` (Z ≥ 1) |
| 받는 것 | 기능 · 유저 체감 변경 | 버그 수정 · 타임라인 보완 |
| 동시에 열린 수 | 1 | 1 |

## 따기와 PR

- **`dev-<버전>`은 `main`에서 딴다.** 버전은 딸 때 정한다. 마이너 dev와 패치 dev는 하나씩 동시에 열 수 있다. 그 이상이 필요하면 먼저 묻는다.
- **작업 브랜치는 해당 `dev-*`에서 따고 그 브랜치로 PR을 낸다.**
- **`main`을 베이스로 PR을 내지 않는다.** `main`에는 `dev-*`만 들어간다(`release.md`).
- ⚠️ **패치 dev에 기능이 섞이게 되면 멈추고 묻는다.** 기능은 마이너 dev로 간다.
- ⚠️ **첫 rc부터 정식까지 `dev-*`에는 rc에서 나온 수정만 머지한다.** 그 밖의 PR은 열어 두고, 릴리즈 뒤 다음 버전 dev로 base를 바꾼다.

## 이름

| 접두사 | 쓰임 | 누가 |
|---|---|---|
| `feat/` · `fix/` · `refactor/` · `test/` · `docs/` | 작업 브랜치. 커밋 타입과 같다 | 에이전트·소유자 |
| `chore/` | 저장소 관리 | 소유자. `chore/version-*`는 Version Bump 자동 생성 |
| `dev-<버전>` · `main` | 위 표 | 소유자 |

- ⚠️ **이 밖의 이름은 원격에 올리지 않는다.** 실험·시안·조사 브랜치는 로컬에서만 쓴다.

## 동기화 — `main`을 `dev-*`에 넣는다

패치가 릴리즈되면 **바로 `main`을 열린 마이너 dev에 넣는다.** 그래야 다음 rc가 패치를 포함한 상태로 검증되고, 정식 머지에서 충돌이 나지 않는다.

1. `dev-*`에서 브랜치를 딴다
2. 그 브랜치에서 로컬로 `git merge origin/main` 하고 충돌을 해결한다
3. 그 브랜치 → `dev-*` PR. CI 3-OS 통과 뒤 머지

- ⚠️ `dev-*`가 이미 rc로 버전을 올렸으면 버전 파일 셋(`pyproject.toml` · `uv.lock` · `APP_VERSION`)이 충돌한다. **`dev-*` 쪽 버전을 남긴다.** 아직 올리지 않았으면 패치 버전이 그대로 들어오고, Auto Tag는 `dev-*`에서 정식 버전이면 태그를 만들지 않는다.
- ⚠️ **`main`을 head로 한 PR을 쓰지 않는다.** GitHub에서 충돌을 해결하면 해결 커밋이 `main`에 생긴다.
- ⚠️ **`dev-*` → `main` PR에서 충돌이 나면 그 PR에서 해결하지 않는다.** 해결 커밋이 마지막 rc 뒤에 생겨 검증 안 된 코드가 정식으로 나간다. 멈추고 동기화부터 한다.

## 작업 브랜치 정리

**PR을 거친 브랜치는 PR이 닫히면(머지·미머지 모두) 지운다.** GitHub가 PR마다 `refs/pull/<번호>/head`를 보관하므로 커밋은 PR에서 받을 수 있다 — `git fetch origin pull/<번호>/head`.

- 머지된 PR의 브랜치는 저장소 설정(Automatically delete head branches)이 지운다. 머지 없이 닫힌 PR의 브랜치는 소유자가 지운다.
- ⚠️ **에이전트는 어떤 브랜치도 지우지 않는다.** 로컬 브랜치 정리가 필요하면 목록만 보고한다.
- ⚠️ **열린 PR의 브랜치와 PR이 없는 브랜치는 지우지 않는다.** 처리는 소유자가 정한다.
